## Abstract

The annotation of genomic variants with their predicted functional consequences is a critical step in genomics research and clinical diagnostics.
The widely used Ensembl Variant Effect Predictor (VEP), implemented in Perl, faces performance limitations when processing the increasingly large variant call sets generated by modern sequencing studies.
Here we present fastVEP, a complete reimplementation of the VEP variant annotation engine in Rust, a systems programming language that combines memory safety with C-level performance.
fastVEP annotates the complete GIAB HG002 clinical whole-genome sequencing benchmark (4.05 million high-confidence variants) against the full Ensembl GRCh38 gene model (509,650 transcripts) in 12 seconds on ten cores.
Benchmarks on complete variant call sets of five organisms, up to 26 million mouse variants and 12.9 million Arabidopsis variants, sustain 326,930 to 553,839 variants per second (for two of the five the variant file is in an older assembly than the gene model, so the figure is of throughput only).
In single-threaded head-to-head benchmarks on the same complete WGS, fastVEP annotates 80-103x faster than Ensembl VEP v115.1, which requires approximately 77 minutes for the equivalent consequence-only run.
A hosted web server is available at https://fastVEP.org.
Against Ensembl VEP 116.3, fastVEP's output on a systematic sample of an ordinary whole-genome call set (186,055 paired rows) agrees in every row on the consequence terms, impact, amino acid and codon changes, positions, flags, gene symbols and biotypes, and in 99.92% of the 5.0 million cells compared; the 3,851 cells that differ are all HGVS descriptions, each with a documented cause, nearly all of them alleles of multi-allelic records that fastVEP describes as each would be alone.
On a 1-in-5 sample of ClinVar 2-star+ variants (84.7 million cells), 99.9965% agree.
Beyond core consequence prediction, fastVEP provides a comprehensive supplementary annotation framework (fastSA) with native binary format for direct integration with ClinVar, gnomAD, dbSNP, COSMIC, 1000 Genomes, TOPMed, and MitoMap databases; prediction and conservation scores including PhyloP, GERP, REVEL, SpliceAI, PrimateAI, and SIFT/PolyPhen via dbNSFP; structural variant annotation (DEL, DUP, INV, CNV, BND) with SV-specific consequence prediction; gene-level annotations from OMIM and gnomAD gene constraint metrics; a filter_vep-compatible expression-based filter engine; multi-sample genotype parsing; and mitochondrial-specific variant handling.
fastVEP supports both GRCh38 and GRCh37 genome builds, ships as a single 5.8 MB executable whose only run-time dependency is the system C library, defines 49 Sequence Ontology consequence terms (38 of which its predictors emit), outputs 49 VEP-compatible CSQ annotation fields, supports VCF, tab-delimited, and JSON output formats, generates HGVS nomenclature, and includes a built-in web interface for interactive variant annotation.
fastVEP is open source under the Apache 2.0 license and is available at https://github.com/Huang-lab/fastVEP.

**Keywords:** variant annotation, variant effect prediction, Rust, genomics, bioinformatics, VCF, HGVS, consequence prediction

## 1. Introduction

The identification and functional interpretation of genomic variants is central to modern genomics research and precision medicine.
With the decreasing cost of whole-genome and whole-exome sequencing, individual studies now routinely generate variant call sets containing millions of variants (The 1000 Genomes Project Consortium, 2015; Karczewski et al., 2020).
Each variant must be annotated with its predicted functional consequence -- whether it causes a missense change in a protein, disrupts a splice site, falls in a regulatory region, or has no predicted effect -- before downstream analysis and clinical interpretation can proceed.

The Ensembl Variant Effect Predictor (VEP) has become the de facto standard tool for variant annotation in the genomics community (McLaren et al., 2016).
VEP predicts the functional effects of genomic variants on genes, transcripts, and protein sequences using Sequence Ontology (SO) terms (Eilbeck et al., 2005).
It supports multiple input and output formats, generates HGVS nomenclature (den Dunnen et al., 2016), and provides a plugin system for extensibility.

However, VEP's implementation in Perl limits its throughput in the era of large-scale genomics: one VEP process annotates hundreds of variants per second in offline mode (876 per second on the whole-genome benchmark of Section 3.2), and a whole genome takes more than an hour.
This becomes increasingly problematic as variant call sets grow to millions of entries in population-scale studies (Taliun et al., 2021) and clinical laboratories require rapid turnaround times.

Several alternative tools have been developed to address performance concerns, including SnpEff (Cingolani et al., 2012), ANNOVAR (Wang et al., 2010), Nirvana (Stromberg et al., 2017), and echtvar (Pedersen, 2023).
Of these, echtvar demonstrated that Rust's systems-level performance combined with compact integer encoding and binary search strategies can achieve million-variant-per-second annotation speeds for population frequency lookups.
However, these tools make different trade-offs in terms of annotation completeness, SO term coverage, and compatibility with the VEP ecosystem.

Here we present fastVEP, a complete reimplementation of the VEP variant consequence prediction engine in Rust (Matsakis & Klock, 2014).
Rust is a systems programming language that guarantees memory safety without garbage collection, enabling both the performance of C/C++ and the safety of managed languages.
fastVEP achieves throughputs of 326,930 to 553,839 variants per second across five model organisms (for two of them, the variant files are in older assemblies than the gene models, so the figure is of throughput only), and annotates a complete human whole genome 80-103x faster than Ensembl VEP v115.1 in single-threaded head-to-head benchmarks -- agreeing with Ensembl VEP 116.3 in 99.92% of 5.0 million cells compared on a whole-genome call set and 99.9965% of 84.7 million on a ClinVar sample, each difference documented, shipping as a single executable with no run-time dependency but the C library, and including a built-in web interface for interactive use.

### 2.2 Data Model

fastVEP's core data model is defined in `fastvep-core` and `fastvep-genome`.
Genomic positions use 1-based, inclusive coordinates consistent with the Ensembl convention.
Variant alleles are represented as an enum distinguishing nucleotide sequences, deletions, missing alleles (`*`), and symbolic alleles (`<DEL>`, `<DUP>`, `<INV>`, etc.) for structural variants.
The `VariantType` enum classifies variants as SNV, insertion, deletion, indel, MNV, or one of seven structural variant types (CopyNumberVariation, CopyNumberLoss, CopyNumberGain, TandemDuplication, Inversion, TranslocationBreakend, ShortTandemRepeatVariation).
The `Consequence` enum encodes 49 Sequence Ontology terms (41 from Ensembl VEP plus 8 SV-specific terms: copy_number_change, copy_number_increase, copy_number_decrease, short_tandem_repeat_change/expansion/contraction, unidirectional_gene_fusion, transcript_variant), each associated with a severity rank and impact classification (HIGH, MODERATE, LOW, MODIFIER).
The predictors produce 38 of the 49.
The other 11 (`mature_miRNA_variant`, `TFBS_ablation`, `TFBS_amplification`, `TF_binding_site_variant`, `regulatory_region_ablation`, `regulatory_region_amplification`, `regulatory_region_variant`, `sequence_variant`, `short_tandem_repeat_expansion`, `short_tandem_repeat_contraction` and `unidirectional_gene_fusion`) are defined and no predictor emits them (`manuscript/data/so_terms.csv`).

Transcript models include full gene structure with exons, coding regions, UTRs, and translation metadata.
The coordinate mapping system supports bidirectional conversion between genomic, cDNA, CDS, and protein positions, correctly handling both forward and reverse strand genes.

### 2.3 VCF Parsing and Allele Normalization

fastVEP's VCF parser handles VCF 4.1+ format with full support for multi-allelic records, structural variant notation, star alleles, and chromosome prefix variants (e.g., `chr1` vs `1`).
The allele normalization logic follows Ensembl VEP's (`Parser::post_process_vfs`):

1. **Single-allele indels:** The bases that the reference and the alternative allele share are stripped from the front and then from the back, until one of them is empty, and the start position moves with the front.
   For example, VCF `POS=100 REF=ATCG ALT=A` becomes Ensembl-format `start=101 ref=TCG alt=-`, and `CAGT>CT` is the deletion of `AG`.

2. **Multi-allelic indels:** The shared first base is stripped only when *all* non-star alleles share the same first base with the reference.

3. **Star alleles:** Preserved unchanged during normalization.

4. **Several ALTs:** An allele of a record with several ALTs is described (`HGVSg`, `HGVSc`, `HGVS_OFFSET`) as it would be if it were alone.
   Ensembl VEP 116 does not do this: what it writes for an allele depends on what else the record holds (divergence 11 of `docs/VEP_DIVERGENCE.md`).

The normalization is tested by 30 integration tests whose records are copied from the test VCF files distributed with VEP release 115 (`vep_compat.rs`), and, for single-allele indels, against Ensembl VEP 116.3 on 1,500 indels written the way a caller that does not trim writes them: every compared column agrees on 3,176 rows but for 26 cells that the test lists and asserts still differ (`docs/VEP_DIVERGENCE.md`, "Lone indels that are not minimal").

### 2.4 Consequence Prediction Engine

The consequence prediction engine is the computational core of fastVEP, implemented in `fastvep-consequence` (5,879 lines).
For each variant, the predictor:

1. **Identifies overlapping transcripts** within a configurable upstream/downstream distance (default 5,000 bp).

2. **Maps the variant to transcript coordinates** using the genomic -> cDNA -> CDS -> protein coordinate mapping system.

3. **Evaluates splice site proximity** across six categories:
   - *Splice donor* (first 2 intronic bases at 5' intron boundary)
   - *Splice acceptor* (last 2 intronic bases at 3' intron boundary)
   - *Splice donor 5th base* (position 5 in intron from donor)
   - *Splice donor region* (positions 3-6 in intron from donor)
   - *Splice polypyrimidine tract* (3 to 17 bases in front of an exon, a window of 15)
   - *Splice region* (3-8 intronic bases or 1-3 exonic bases from any junction)

4. **Determines coding consequences** by:
   - Mapping the variant to the affected codon(s) using the translateable sequence
   - Translating reference and variant codons using the NCBI standard genetic code
   - Classifying the amino acid change: synonymous, missense, nonsense (stop gained), stop lost, start lost, or start retained
   - Identifying frameshift vs. in-frame indels based on whether the length change is divisible by three
   - For frameshifts, scanning the altered reading frame to determine the new termination codon position

5. **Handles non-coding transcripts** by assigning `non_coding_transcript_exon_variant` for exonic positions and `non_coding_transcript_variant` (combined with `intron_variant` where applicable) for intronic positions, bypassing the coding consequence pathway entirely.

6. **Appends the `NMD_transcript_variant` modifier** for any transcript annotated with the `nonsense_mediated_decay` biotype, regardless of the primary consequence.
   This modifier is added after all other consequence terms and before deduplication, matching Ensembl VEP's behavior of flagging variants in transcripts predicted to undergo nonsense-mediated mRNA decay.

7. **Assigns the most severe consequence** across all transcripts for summary reporting.

### 2.5 HGVS Nomenclature

fastVEP generates HGVS nomenclature following the Human Genome Variation Society guidelines (den Dunnen et al., 2016):

- **HGVSg** (genomic): `chr1:g.12345A>G`, `chr1:g.100_102del`, `chr1:g.100_101insTCG`
- **HGVSc** (coding DNA): `ENST00000001:c.51A>G`, `ENST00000001:c.4_6del`
- **HGVSp** (protein): `ENSP00000001:p.Arg41Lys`, `ENSP00000001:p.Arg41Ter`, `ENSP00000001:p.Ala527ProfsTer48`

Notation types include substitutions, deletions, insertions, deletion-insertions (delins), duplications, frameshifts with termination position, stop-lost extensions carrying the extension length (`p.Ter100GlnextTer17`, falling back to `extTer?` only where the extended frame reaches the end of the transcript without another stop), and synonymous variants (`p.Arg41=`).

HGVSp is a transcription of Ensembl VEP's own `hgvs_protein` (release 116), one function to each of the routines it calls, so that its output can be compared with VEP's string by string.
Ensembl's notation is not derived from the protein the change produces.
The change is first moved to its most 3' position over the genome, as for HGVSc, and the notation is then a sequence of operations on two short peptides: the residues of the codon window the change edits there, before and after.
The residues the two share at either end are clipped, the type (substitution, deletion, insertion, duplication, delins, frameshift, extension) follows from what is left, and an insertion or a deletion is moved along the protein while it repeats the residue after it.
For a frameshift the first residue whose translation differs is found by translating the CDS with the change applied and the 3' UTR appended, and the new stop is counted from there: `p.Ala498ProfsTer28` names the first changed residue (Ala498), the residue now at that position (Pro) and the distance to the new stop (Ter28).
The same translation counts the extension of a lost terminator (`p.Ter100GlnextTer17`).
When the frame runs to the end of the transcript without another stop the count is `?` (`fsTer?`, `extTer?`).
A change that loses the initiator is written `p.Met1?` (`p.Leu1?` for a transcript whose first residue is a Leu), as HGVS names it.
Ensembl writes `p.Xxx1?` for most of these changes and a range, another residue or nothing for the rest, and that is a deliberate difference (divergence 15 of `docs/VEP_DIVERGENCE.md`).

### 2.6 Output Formats

fastVEP supports three output formats:

1. **VCF output** adds a `CSQ` INFO field with 49 pipe-delimited annotation fields matching Ensembl VEP's extended format: Allele, Consequence, IMPACT, SYMBOL, Gene, Feature_type, Feature, BIOTYPE, EXON, INTRON, HGVSc, HGVSp, cDNA_position, CDS_position, Protein_position, Amino_acids, Codons, Existing_variation, REF_ALLELE, UPLOADED_ALLELE, DISTANCE, STRAND, FLAGS, CANONICAL, SYMBOL_SOURCE, HGNC_ID, MANE, MANE_SELECT, MANE_PLUS_CLINICAL, TSL, APPRIS, CCDS, ENSP, SOURCE, HGVS_OFFSET, SIFT, PolyPhen, AF, CLIN_SIG, SOMATIC, PHENO, PUBMED, MOTIF_NAME, MOTIF_POS, HIGH_INF_POS, MOTIF_SCORE_CHANGE, TRANSCRIPTION_FACTORS, ACMG, and ACMG_CRITERIA.
   The five regulatory columns (the motif fields and TRANSCRIPTION_FACTORS) are in the header for compatibility with VEP and are written empty, and ACMG and ACMG_CRITERIA are filled by `--acmg`.
   Special characters are escaped following VEP conventions: commas -> `&`, semicolons -> `%3B`, pipes -> `&`.

2. **Tab-delimited output** produces one line per variant-allele-transcript combination with 17 columns: 13 of the default columns of Ensembl VEP's tab output, and IMPACT, DISTANCE, STRAND and FLAGS, which VEP writes among its extra fields.

3. **JSON output** provides a structured representation with nested transcript consequence arrays, suitable for programmatic consumption.

### 2.7 Annotation Source Architecture

fastVEP uses a trait-based provider architecture for annotation sources:

- `TranscriptProvider`: Returns transcripts overlapping a genomic region.
  The `IndexedTranscriptProvider` implementation groups transcripts by chromosome into sorted arrays and uses two binary searches (`partition_point`) to bound each overlap query: one over the start-sorted list for the last transcript that begins at or before the query, and one over a per-chromosome prefix maximum of transcript end positions for the first transcript that can still reach back to it.
  The cost is O(log n + s), where n is the number of transcripts on the chromosome and s is the width of the bounded window — s is O(n) in the worst case (a transcript spanning the chromosome holds the window open) but averages 17 entries over random queries against Ensembl 116 chromosome 22.
  This approach, inspired by echtvar's chunked binary search strategy (Pedersen, 2023), replaces naive linear scans and is critical for performance when annotating against large gene models (e.g., the 11,615 transcript records of chromosome 22 in the Ensembl 115 GFF3).
- `SequenceProvider`: Provides reference sequences for regions.
  Implemented via `FastaSequenceProvider` with memory-mapped FASTA support using `.fai` index files for zero-copy reference access via the `memmap2` crate.
- `VariationProvider`: Looks up co-located known variants via tabix-indexed VEP cache files (`all_vars.gz` per chromosome).
  The `TabixVariationProvider` implementation performs allele-aware matching that accounts for multi-allelic sites, strand orientation (with automatic reverse-complement matching for minus-strand records), and VCF-to-Ensembl deletion marker normalization.
  For each matched variant, the provider extracts the dbSNP identifier, allele-specific population frequencies (gnomAD, 1000 Genomes continental populations), minor allele frequency, clinical significance, somatic status, phenotype/disease associations, and PubMed references.
  These annotations populate the `Existing_variation`, `AF`, `CLIN_SIG`, `SOMATIC`, `PHENO`, and `PUBMED` CSQ output fields.

Several performance optimizations reduce startup and annotation latency:

1. **O(T+E) indexed GFF3 assembly**: Transcript assembly from GFF3 features uses an indexed approach with O(T+E) complexity (where T = transcripts and E = exons), replacing an earlier O(T*E) nested iteration.
   Parsing the whole human gene model (509,650 transcripts, 1.2 GB) and building the cache takes 13.0 seconds on ten cores.
2. **Binary transcript cache**: Transcripts parsed from GFF3 are serialized with bincode into zstd frames of about 8 MB, with a table of the frames at the end of the file that a run on more than two threads uses to decode them side by side.
   A run of one variant takes 0.03 seconds for the 7K-transcript yeast model and 0.91 seconds on one thread (0.41 on eight) for the 510K-transcript human model.
3. **Tabix-indexed GFF3 loading**: When a tabix index (.tbi) is available for the GFF3 file, fastVEP loads only transcripts overlapping the variant regions, further reducing startup time and memory usage.
4. **Memory-mapped FASTA**: Reference sequences of an uncompressed FASTA are accessed via memory-mapped I/O using `.fai` index files, providing zero-copy access without loading the entire genome into memory.
5. **One pass per record**: Each record is annotated, rendered and freed by the thread that takes it, each batch is written on a thread of its own, and the pick (`--pick*`) is made before the rows of a record are built, so that a run with a large `--distance` builds only the rows it keeps.
6. **mimalloc**: The `fastvep` binary uses the mimalloc allocator.
   On Linux it avoids glibc's growing of the arena of each thread a page at a time, which made 231,689 `mprotect` calls while the cache was decoded on 8 threads against 62 with mimalloc, at the price of 4 to 9% more peak memory.

This trait-based design allows transparent substitution of annotation sources -- for example, replacing the GFF3 provider with a binary cache reader or the tabix variation provider with a database-backed implementation -- without modifying the prediction engine.

### 2.8 Web Interface

fastVEP includes a built-in web interface accessible via `fastvep web --gff3 <file> --fasta <file> --port 8080`.
The interface is a single-page application (2,650 lines of HTML/CSS/JavaScript) embedded directly in the binary using Rust's `include_str!` macro, requiring no external files or dependencies.

The web interface operates in two modes.
When served by the fastVEP binary (`fastvep web`), annotation requests are handled by the Rust backend via a REST API (`POST /api/annotate`) through the shared annotation engine.
The embedded server handles one connection at a time and has no supplementary-annotation directory; the standalone production server (`fastvep-web`, axum and tokio) serves requests concurrently and loads supplementary annotations.
Users can upload custom GFF3 files through the browser, which are parsed server-side by the Rust GFF3 parser (`POST /api/upload-gff3`), avoiding the latency of client-side parsing for large annotation files.
When deployed as a static page (e.g., GitHub Pages), the interface falls back to a client-side JavaScript annotation engine that reimplements core consequence prediction logic for interactive use without a server.

The web interface features:
- A VCF input area with example datasets (coding, splicing, non-coding variants)
- Custom GFF3 file upload with server-side or client-side parsing
- Configurable annotation options (upstream/downstream distance, pick mode for canonical transcripts)
- Light/dark mode with system preference detection
- An interactive results table with all annotation fields (HGVSg/c/p, canonical, strand, distance), column sorting, and search/filter
- A summary view with bar charts showing impact and consequence distributions
- Raw output in VCF (CSQ), tab-delimited, or JSON format
- Automatic backend detection with transparent fallback to client-side annotation

### 2.9 Supplementary Annotation Framework (fastSA)

fastVEP includes a native supplementary annotation framework (fastSA) for direct integration with clinical and population databases, inspired by Illumina Nirvana's NSA architecture (Stromberg et al., 2017).
The framework defines three binary file formats:

1. **Position/allele-level annotations (.osa / .osa2):** Two format generations are supported.
   The v1 format (.osa) uses zstd block-compressed data files with per-chromosome indexing and memory-mapped I/O.
   The v2 format (.osa2), inspired by echtvar's high-performance architecture (Pedersen, 2023), uses ZIP-based archives with ~1MB genomic chunks (position >> 20), compact 32-bit variant encoding (Var32: 20-bit position + 2-bit ref_len + 2-bit alt_len + 8-bit encoded bases), parallel u32 value arrays instead of JSON strings, delta encoding for variant keys, float quantization (value * multiplier -> u32), categorical string-to-index encoding, and zigzag encoding for signed values.
   The v2 format eliminates JSON parsing from the hot path and enables O(log n) binary search on 4-byte keys instead of variable-length string comparisons; chunks are read lock-free directly from the memory-mapped archive (the ZIP central directory is parsed once at open).
   Both format generations decompress into a single process-wide, thread-scaled, byte-budgeted LRU cache shared across all open sources, sized to the parallel working set so that a dense whole-genome source (e.g. SpliceAI or dbSNP) queried in parallel is read once rather than re-decompressed per worker, while total cache memory stays bounded regardless of how many per-chromosome shards are open.

2. **Interval-level annotations (.osi):** For structural variant databases (gnomAD SV, ClinGen dosage, DGV) where annotations are genomic regions.
   Supports overlap queries with reciprocal overlap calculation.

3. **Gene-level annotations (.oga):** For gene-keyed databases (OMIM, gnomAD gene constraint metrics) where annotations are looked up by gene symbol.

The `AnnotationProvider` trait defines the interface for all supplementary sources, supporting batch preloading (decompress relevant blocks before parallel annotation) and thread-safe parallel querying via Rust's `Send + Sync` constraints.
The `sa-build` CLI subcommand builds fastSA files from standard source formats:

- **Clinical databases:** ClinVar (VCF: CLNSIG, CLNREVSTAT, CLNDN), dbSNP (VCF: RS IDs, global MAF), COSMIC (VCF: COSV IDs, gene, sample counts)
- **Population frequencies:** gnomAD (VCF: AF per population; v2 exomes/genomes through v4.0 and v4.1, including v4.1 joint frequencies), 1000 Genomes (VCF: 5 continental populations), TOPMed (VCF: AF, AC, AN), MitoMap (TSV: disease, status)
- **Prediction scores:** PhyloP (wigFix), GERP (TSV), DANN (TSV), REVEL (CSV), SpliceAI (VCF: delta scores), PrimateAI (TSV), AlphaMissense (TSV: pathogenicity score/class), dbNSFP (TSV: SIFT/PolyPhen)
- **Gene-level:** OMIM genemap2 (TSV: MIM numbers, phenotypes), gnomAD gene constraint (TSV: pLI, LOEUF, mis_z, syn_z)

By default (`--format auto`), `sa-build` writes the v2 `.osa2` format for the allele- and position-level sources it supports and the v1 `.osa` format otherwise; both formats are queried transparently at annotation time.

### 2.10 Structural Variant Support

fastVEP supports annotation of structural variants including deletions (`<DEL>`), duplications (`<DUP>`, `<DUP:TANDEM>`), inversions (`<INV>`), copy number variants (`<CNV>`, `<CN0>`-`<CN4>`), breakends (`<BND>`), insertions (`<INS>`), and short tandem repeats (`<STR>`).
The VCF parser detects symbolic alleles, parses the SV-specific INFO fields SVTYPE, END and SVLEN, and classifies each variant into one of the `VariantType` categories.

The `SvConsequencePredictor` determines consequences based on the overlap between the SV interval and transcript models:
- **Complete containment:** transcript_ablation (for deletions) or transcript_amplification (for duplications)
- **Partial overlap:** feature_truncation, feature_elongation, coding_sequence_variant (if CDS affected), splice_acceptor_variant (if splice sites affected)
- **Copy number:** copy_number_change, copy_number_increase, copy_number_decrease
- **Breakends:** transcript_variant, coding_sequence_variant (if landing in CDS)
- **Repeat expansions:** short_tandem_repeat_change

### 2.11 Filter Engine

fastVEP implements a filter engine compatible with Ensembl VEP's filter_vep tool.
The engine consists of three components: (1) a tokenizer that handles field names, comparison operators (is, !=, <, >, <=, >=, in, match), logical operators (and, or, not), and parenthesized grouping; (2) a recursive-descent parser producing a typed AST; and (3) an evaluator that resolves field values from annotation output and applies the filter logic.
String comparisons are case-insensitive, numeric comparisons parse field values to f64, and the `in` operator supports ampersand-separated VEP consequence fields.

### 2.12 Multi-Sample Parsing and Mitochondrial Variants

fastVEP parses VCF FORMAT and sample columns to extract per-sample genotype (GT), depth (DP), genotype quality (GQ), and allele depth (AD) information.
Genotypes are classified as het, hom_ref, hom_alt, or missing, enabling trio-based filtering (e.g., de novo variant detection).

The library has a parser and an interval index for Ensembl regulatory-build GFF3 files (promoters, enhancers, CTCF and transcription-factor binding sites, open chromatin), but no command or server calls them: fastVEP does not annotate regulatory features in this release, `--regulatory` is refused, and the motif columns of the CSQ field are empty.
Mitochondrial variants are handled with circular coordinate wrapping and the vertebrate mitochondrial codon table (NCBI translation table 2), which differs from the standard table at AGA/AGG (Stop instead of Arg), ATA (Met instead of Ile), and TGA (Trp instead of Stop).

### 2.13 Implementation Language Choice

Rust was chosen for fastVEP based on several properties relevant to bioinformatics tool development:

1. **Zero-cost abstractions**: Generic code compiles to direct function calls; the provider traits are also used as trait objects (`Box<dyn AnnotationProvider>`), at the price of one virtual call per lookup.
2. **Memory safety without garbage collection**: Rust's ownership system eliminates entire classes of bugs (use-after-free, data races, null pointer dereferences) while avoiding the unpredictable pause times of garbage-collected languages.
3. **Self-contained executables**: fastVEP compiles to a single 5.8 MB executable whose only run-time dependency is the system C library (libSystem on macOS, glibc 2.34 or newer for the Linux archives), simplifying deployment in HPC environments, Docker containers, and clinical pipelines.
4. **Ecosystem maturity**: The Rust bioinformatics ecosystem includes production-quality crates for genomic file formats (noodles, rust-htslib), interval trees (coitrees), and parallelism (rayon).

### 3.1 Throughput Performance

We benchmarked fastVEP against Ensembl VEP v115.1 on the GIAB HG002 v4.2.1 benchmark VCF (4,048,342 high-confidence variants), using identical inputs for both tools: the full Ensembl GRCh38 release 115 GFF3 gene model (509,650 transcripts as fastVEP reads it), the GRCh38 primary-assembly FASTA reference, and equivalent options (`--hgvs --symbol --canonical`).
To isolate raw engine efficiency, both tools were run single-threaded (Tables 2-3, Figure 2).
fastVEP used its binary transcript cache; Ensembl VEP ran via Docker (`ensemblorg/ensembl-vep:release_115.1`) in indexed `--gff` mode against a bgzip+tabix-indexed GFF3.
The fastVEP times are those of 7 November 2026, measured with the release candidate v0.5.0-rc.1 of fastVEP; the Ensembl VEP times are those of 29 July 2026, measured on the same Apple M4 and not repeated here (Methods).

We first measured how the comparison scales with input size on chromosome 22 (Table 2).

### 3.2 Clinical Whole-Genome Head-to-Head

At genome scale the fixed startup cost is fully amortized and fastVEP's advantage is largest.
On the complete GIAB HG002 WGS, fastVEP is 80-103x faster than Ensembl VEP single-threaded, across consequence-only and annotation-augmented workloads (Table 3).
A single-process whole-genome VEP run exhausts the default container memory above ~2.7 million variants, because transcript structures accumulate across the genome as annotation proceeds; VEP's genome-wide time was therefore measured per chromosome and summed, which also bounds its resident memory to a single chromosome and represents its best case.
Each per-chromosome time is the minimum of two runs, to remove transient system contention (Methods).

The 5 consequence-only runs behind the medians ranged from 43 to 55 seconds on one thread and from 12 to 17 seconds on ten threads (every run is in `benchmarks/results/`).
With its default multi-threaded pipeline (10 cores: 4 performance and 6 efficiency), fastVEP annotates the same complete WGS in 12 seconds (335,767 variants per second) on this system -- about 3.7x its single-threaded speed and in line with the 12 seconds of the multi-organism benchmark (Table 7), which runs the same genome with `--hgvs` alone.
These results demonstrate that fastVEP annotates a complete clinical WGS in under 20 seconds -- fast enough for routine integration into clinical sequencing pipelines, where variant annotation has traditionally been a multi-hour step.
The practical gap is widest exactly where it matters most for population- and clinical-scale work: the complete human genome.

These whole-genome VEP times are **directly measured** (each chromosome run separately and the wall-clock times summed) rather than extrapolated.
They supersede an earlier version of this benchmark, which projected VEP's full-genome runtime from chromosome 22 throughput and reported a substantially larger nominal speedup; that projection extrapolated a slower per-variant rate and did not correspond to a like-for-like measured run on an identically indexed gene model.
In the present comparison both tools consume the **same bgzip/tabix-indexed** GRCh38 release 115 GFF3 at every scale, and VEP's full-genome result was obtained the only way it completes within the available memory -- per chromosome, then summed -- yielding a conservative, reproducible 80-103x single-threaded advantage for fastVEP.

### 3.3 Annotation Accuracy Against Ensembl VEP

fastVEP's output was compared with that of Ensembl VEP, the implementation it ports.
VEP ran in Docker (`ensemblorg/ensembl-vep:release_116.3`) in `--gff` mode over the same GRCh38 Ensembl 115 GFF3 and FASTA that fastVEP reads, with `--tab --symbol --biotype --canonical --numbers --variant_class --show_ref_allele --hgvs --hgvsg`, and `validation/compare_tab.py` paired the rows of the two outputs on (variant, allele, transcript) and compared them cell by cell: 27 columns with the HGVS columns and 23 without them (`SYMBOL_SOURCE`, `HGNC_ID` and `FLAGS` are left out, because a GFF3 carries none of them and VEP's `--gff` reader writes `-`, where fastVEP, like VEP's own cache, fills them).
Release 116.3 is the one most users run now, and fastVEP follows it where it differs from release 115.1, the release of the timing comparison, among other points in the protein version of an HGVSp description, the predicates of the coding consequence terms and the frameshift introns.
The comparison with 115.1 that the repository also holds (September 2026) was made with an earlier build, v0.3.0, whose output differs from this release's on every input of the comparison (`benchmarks/results/v0.5.0-rc.1/identity_vs_ac2e2b6/`), so it is not reported as this release's.

The comparisons below were made on 27 October 2026 with the build at commit 5048fc5.
Ensembl VEP's output does not depend on the build of fastVEP it is compared with, so they describe any build that writes the same bytes, and the release candidate does: its output and that build's are byte-identical, as a VCF and as a table with the flags of this comparison, on the 173 variants of the VEP example set, the stratified ClinVar sample of 6,600 variants, the 1-in-5 sample of the ClinVar 2-star+ set that is compared below, the 1-in-200 sample of HG002 that is compared below and the 400 in-frame deletions, and as a VCF on the whole HG002 call set (4,048,342 records, 11.1 GB; 11 runs in all; `validation/compare_builds.py`, `benchmarks/results/v0.5.0-rc.1/identity_vs_5048fc5/`).

On a systematic 1-in-200 sample of the GIAB HG002 call set (20,241 variants, 186,055 paired rows, 5,023,485 cells), `Consequence`, `IMPACT`, `Amino_acids`, `Codons`, `cDNA_position`, `CDS_position`, `Protein_position`, `Location`, `REF_ALLELE`, `VARIANT_CLASS`, `DISTANCE`, `STRAND`, `FLAGS`, `EXON`, `INTRON`, `SYMBOL` and `BIOTYPE` agree on every paired row (Figure 3A), and 3,851 cells (0.077%) differ, all of them in four HGVS columns: `HGVS_OFFSET` 2,070, `HGVSc` 1,729, `HGVSg` 35 and `HGVSp` 17.
Each has a documented cause (Figure 3B).
3,822 are alleles of records with several ALTs, which fastVEP describes as each would be alone and Ensembl 116, which no longer splits such a record, describes by what else the record holds (divergence 11 of the repository's record).
12 are an intronic base after the terminator, where Ensembl writes the offset with a `*` in place of its exonic anchor (`c.*4395G>A` for `c.174+4395G>A`; divergence 4).
17 are a change that the 3'-rule carries over an intron, for which fastVEP writes the protein change and Ensembl none (divergence 17).
Rows that only one tool writes are rare: 121 of fastVEP's, all on transcripts, and 7 of VEP's; the transcripts looked at are of feature types that VEP's `--gff` reader does not keep (not all were checked).

On a systematic 1-in-5 sample of the ClinVar 2-star+ call set (134,732 variants, 3,136,295 paired rows) 112 of 72,134,785 cells (0.00016%) differ without the HGVS columns, and 2,999 of 84,679,965 (0.0035%) with them.
Without the HGVS columns, 91 of the 112 cells are on transcripts that fastVEP flags as incomplete, where VEP's `--gff` reader, which has no flags, writes `start_lost`, `stop_lost` or `stop_retained_variant` for a change in a transcript with no start or stop codon to lose, 12 are divergence 14 (a start codon is not lost where the protein still begins with its Met), and the other 9 disappear when the UTR of a reverse-strand transcript, which VEP's `--gff` reader builds from the wrong region, is corrected.
Most users run VEP from its cache and not from a GFF3: against the output of VEP 116.3's own Ensembl cache for chromosomes 21 and 22 (`vep --cache --offline`), fastVEP over the matching GFF3 differs in one `Consequence` cell of the 168,813 paired rows of the same sample.

A real call set holds few of the shapes on which two implementations can differ, so the comparison was repeated on worlds built to be hard: a generated world of 3,000 records on both strands with coding and non-coding genes, 372 of them with several ALTs (7,213 paired rows, 954 of 216,390 cells differ, 0.44%); the same world's edges, every shape of change within ten bases of every exon, CDS and transcript boundary, each its own record (17,672 records, 36,958 rows, 845 of 1,108,740 cells, 0.076%); and its lone indels written with shared bases (1,500 records, 26 of 95,280 cells, 0.027%).
Smaller worlds of the same kinds, with the output that VEP 116.3 wrote for them, are fixtures of the test suite (20,363 records in nine fixtures), and the 26 tests that compare fastVEP's output with them passed in the run of this release.

Every row on which the two tools disagree is enumerated and attributed in the repository's divergence record (`docs/VEP_DIVERGENCE.md`), which separates the cases where fastVEP deliberately does not reproduce Ensembl's output from the gaps where Ensembl is right and the defect is fastVEP's.
One example of the first kind is a two-residue deletion in the poly-glutamate C-terminus of NT5C2 (ENSP00000502205, `10:103089678 TTCCTCC>T`), for which fastVEP writes `p.Glu560_Glu561del`, the 3'-most placement that HGVS asks for, and Ensembl `p.Glu559_Glu560del`.
Ensembl stops short of the end of the protein in two ways, both of which are in release 116 as they were in 115: `_shift_3prime` halts n-1 residues before the terminus for an n-residue change, and the residues it looks at come from `_get_surrounding_peptides`, which returns nothing when a change ends one residue short of the end, so that such a change, which is NT5C2's, is not shifted at all.

**Table 4. Resource usage comparison between fastVEP and Ensembl VEP.**

fastVEP's binary transcript cache (bincode serialization in zstd frames of about 8 MB, with a table of the frames at its end, so that a run on more than two threads decodes them side by side) makes a run of one variant take 0.03 seconds for the 7K-transcript yeast model and 0.91 seconds on one thread (0.41 seconds on eight) for the 510K-transcript human model, almost all of it reading the cache.
Ensembl VEP's start-up in `--gff` mode was not measured by itself: its whole run of 1,000 variants of chromosome 22 took 0.45 seconds in July (Table 2), which bounds it from above, because it fetches only the regions of the GFF3 that its input overlaps; this is the trade-off of Section 3.1, in which fastVEP pays for the whole gene model at the start of every run and VEP does not.
The first run on a gene model, which parses the GFF3 and writes the cache, takes 13.0 seconds on ten cores for the human model, and the cache is 129 MB.
The cache holds the whole gene model with its sequences in memory: a run of 100,000 variants peaks at 2.6 GiB whatever the number of threads (2.62 GiB on one, 2.64 GiB on eight, 2.65 GiB on ten) and, without a FASTA (consequence prediction only, no HGVS), at 1.2 GiB.
The release binary is compiled with LTO, a single codegen unit and stripped symbols (5.8 MB).
Variants are processed in a streaming fashion without buffering the entire input in memory, so peak memory is the gene model and not the variants (a run of one variant peaks at 2.57 GiB), and memory-mapped FASTA access avoids loading the full reference genome.

## 4. Discussion

### 4.1 Performance Implications

Benchmarks on the GIAB HG002 gold-standard dataset demonstrate that fastVEP annotates a complete human WGS 80-103x faster than Ensembl VEP single-threaded (Table 3), and completes the same genome in about 12 seconds (~335,767 variants per second) with its default multi-threaded pipeline.
The fixed binary-cache start-up of 0.9 seconds dominates only at small variant counts; as input grows, single-threaded throughput rises to 90,484 variants per second on the full 4.05M-variant WGS, demonstrating efficient amortization of the start-up cost.

The practical implications are substantial: annotating 500,000 variants takes roughly 6 seconds with single-threaded fastVEP (about 2 seconds multi-threaded; extrapolated from the whole-genome runs, not run), compared to approximately 10 minutes with single-threaded Ensembl VEP at its measured 876 variants per second.
For population-scale studies processing millions of variants, this is the difference between minutes and hours.

Six optimizations underpin this performance: (1) O(T+E) indexed GFF3 assembly, (2) a binary transcript cache, written as zstd frames and decoded side by side, eliminating repeated GFF3 parsing, (3) tabix-indexed GFF3 loading restricting parsing to variant-overlapping regions, (4) memory-mapped FASTA providing zero-copy reference access, (5) a single pass per record, in which each record is annotated, rendered and freed by the thread that takes it, each batch is written on a thread of its own, and the pick is made before the rows of a record are built, and (6) the mimalloc allocator, which on Linux avoids glibc's growing of the arena of each thread a page at a time (231,689 `mprotect` calls to decode the cache on 8 threads against 62), at a cost of 4 to 9% more peak memory.
Together, these reduce the startup-dominated bottleneck that previously limited real-data throughput.

### 4.2 Accuracy Validation

Against Ensembl VEP 116.3, fastVEP's output on a systematic sample of an ordinary whole-genome call set agrees on every paired row in the columns that carry a consequence call, an impact, a protein or codon change, a position, a flag or a gene symbol and biotype, and in 99.92% of the 5.0 million cells compared; the 3,851 that differ are HGVS descriptions that each have a documented cause, 99.2% of them alleles of multi-allelic records, which fastVEP describes as each would be alone (Section 3.3).
On a 1-in-5 sample of the ClinVar 2-star+ call set, 99.9965% of 84.7 million cells agree, HGVS columns included.
On the generated worlds built to be hard, 99.56%, 99.92% and 99.97% of the cells agree.

These numbers are those of the build of 27 October 2026, and the release candidate writes the same bytes as it does on every input that can be compared without VEP (Section 3.3), so they are the release candidate's; they were not measured again with VEP for this release.

Where HGVS or the Sequence Ontology says that Ensembl's output is wrong, fastVEP does not reproduce it, and the divergence record lists every such case with the row counts.
A nomenclature string that enters a clinical record should follow the standard even where the reference implementation does not, and the 3'-maximal placement of a deletion at a protein terminus (NT5C2, Section 3.3) is the plainest example.
The record also lists, as gaps, the cases in which Ensembl is right.

### 4.3 Splice Site Categories

fastVEP implements the six categories of splice-site consequences that Ensembl VEP 115.1 writes: splice donor, splice acceptor and splice region, and the three that the Sequence Ontology adds for a finer classification, `splice_donor_5th_base_variant`, `splice_donor_region_variant` and `splice_polypyrimidine_tract_variant` (all six occur in the genome-wide distribution of Table 8, and the ranges follow VEP's own).
The finer terms, defined in the Sequence Ontology but often omitted by annotation tools, provide more granular classification of variants near splice sites.
This is particularly relevant for the interpretation of variants of uncertain significance (VUS) in clinical genomics, where splice effects are a common mechanism of pathogenicity (Jaganathan et al., 2019).

### 4.4 Architectural Design Decisions

Several design decisions in fastVEP's architecture merit discussion:

**Modular crate structure.**
The twelve-crate workspace allows independent compilation and testing of components, improving development velocity and code quality.
The trait-based provider architecture (`TranscriptProvider`, `SequenceProvider`, `VariationProvider`, `AnnotationProvider`, `GeneAnnotationProvider`) enables transparent substitution and composition of data sources without modifying the prediction engine.
The `fastvep-sa` crate, added to provide clinical database integration, follows the same composable pattern -- annotation providers are discovered at runtime from the `.osa`, `.osa2`, `.oga` and `.osi` files in the `--sa-dir` directory and plugged into the parallel annotation loop automatically.

**Indexed transcript lookup.**
fastVEP's transcript overlap queries use per-chromosome sorted arrays with binary search, inspired by the chunked binary search strategy employed in echtvar (Pedersen, 2023) for fast variant-to-annotation matching.
Two binary searches bound each query (Section 2.7), giving O(log n + s) query complexity against the O(n) linear scan of a naive implementation.
The width s counts the transcripts examined, not the ones returned: a transcript that stays open across the chromosome holds the window open with it, so s is O(n) in the worst case even though it stays small on real gene models.
The distinction matters when annotating against large gene models containing tens of thousands of transcripts per chromosome.

**GFF3 as primary annotation source with binary caching.**
Unlike Ensembl VEP, which relies on pre-built caches in Perl's Storable/Sereal serialization format, fastVEP uses standard GFF3 files as its primary transcript source.
This eliminates the dependency on Perl-specific serialization and leverages a widely supported standard format.
To avoid the cost of repeated GFF3 parsing, fastVEP implements a binary transcript cache using bincode serialization in zstd frames.
On first run, transcripts are parsed from GFF3 and cached; subsequent runs load from cache (a run of one variant takes 0.03 seconds for yeast and 0.91 seconds on one thread, 0.41 on eight, for the full human genome).
Additionally, when a tabix index is available for the GFF3 file, fastVEP loads only transcripts overlapping the input variant regions, further reducing startup time and memory usage.

**49-field CSQ output.**
fastVEP outputs 49 annotation fields in its CSQ format, exceeding VEP's default 30-field output.
The additional fields (CANONICAL, CCDS, ENSP, MANE, MANE_SELECT, MANE_PLUS_CLINICAL, SIFT, PolyPhen, AF, CLIN_SIG, SOMATIC, PHENO, PUBMED, HGVS_OFFSET, ACMG and ACMG_CRITERIA) provide comprehensive downstream analysis data in a single annotation pass; the five regulatory columns are present and empty.

**Hybrid web architecture.**
The web interface supports both server-side and client-side annotation.
When served by the fastVEP binary, annotation requests are processed by the Rust backend through the shared annotation engine.
GFF3 files uploaded through the browser are parsed server-side, avoiding the performance limitations of JavaScript parsing for large annotation files.
For static deployments (e.g., GitHub Pages), the interface transparently falls back to a client-side JavaScript annotation engine, enabling offline use after page load at the cost of reduced performance and a maintenance burden of mirroring the Rust logic.

## 5. Methods

### 5.1 Implementation

fastVEP is implemented in Rust (2021 edition; the toolchain is the `stable` channel that `rust-toolchain.toml` names, 1.98.0 for the measurements below).
The project is a Cargo workspace with twelve member crates.
External dependencies are limited to: `clap` (CLI parsing), `serde`/`serde_json`/`bincode`/`toml` (serialization), `anyhow`/`thiserror` (error handling), `flate2` (gzip decompression, and DEFLATE inflation of `.osa2` ZIP entries), `zstd` (zstandard compression of the transcript cache and of the v1 fastSA format), `zip` and `lru` (the v2 `.osa2` chunked-archive format and the shared block/chunk caches), `log`/`env_logger` and `tracing` (logging), `memmap2` (memory-mapped I/O), `noodles-bgzf`/`noodles-core`/`noodles-csi`/`noodles-tabix` (tabix-indexed file access), `rayon` (parallelism), `foldhash` (a hasher), `mimalloc` (the allocator of the `fastvep` binary) and `tempfile` (atomic output).
The standalone web server (`fastvep-web`) additionally uses `axum`, `tokio`, `tower`, `tower-http` and `tracing-subscriber`.
Two of these compile C code (`zstd-sys` builds libzstd and `libmimalloc-sys` builds mimalloc), so building needs a C compiler, and the program uses `unsafe` for memory-mapped files and for its global allocator.

### 5.2 Benchmarking

All fastVEP benchmarks were performed on an Apple MacBook Pro with an Apple M4 chip (10 cores: 4 performance and 6 efficiency; 24 GiB of memory) running macOS 26.5.1 (Darwin 25.5.0), on 7 November 2026, while nothing else of ours ran (the load average at the start of the run, which counts the operating system's own processes, was 3.49).
The fastVEP binary was built from the release candidate v0.5.0-rc.1 (commit c12d9f9) with `cargo build --release -p fastvep-cli` (rustc 1.98.0; release profile with fat LTO, one codegen unit and stripped symbols; SHA-256 0063e01bd143...).
The harness is `benchmarks/run_head_to_head.py` (the chromosome 22 series, the whole genome, start-up, peak memory and output formats) and `benchmarks/run_benchmark.sh` (the five organisms), and every run, the machine, the hash of the binary and of every input are in `benchmarks/results/v0.5.0-rc.1/`.
Each cell is run once per round for 5 rounds, after one round that is not reported (it reads every input once and is where the outputs are hashed), and the median is reported (the five organisms: the median of 5 runs of `run_benchmark.sh`); the multi-threaded outputs were compared with the single-threaded ones byte for byte (md5) and were identical.
Peak memory is the peak resident set size of the process, as the operating system reports it once the process has exited.

Throughput benchmarks used the GIAB HG002 v4.2.1 high-confidence benchmark VCF (4,048,342 variants; Zook et al., 2019) annotated against full Ensembl GRCh38 release 115 GFF3 annotations (509,650 transcripts as fastVEP reads them) with the GRCh38 primary-assembly FASTA reference and HGVS nomenclature enabled.
fastVEP used its binary transcript cache (bincode in zstd frames), which the harness rebuilds with the binary being measured before it times anything.

For the head-to-head comparison, both tools were run single-threaded, fastVEP with `RAYON_NUM_THREADS=1`.
Ensembl VEP v115.1 (Docker image `ensemblorg/ensembl-vep:release_115.1`) was run in `--gff` mode against a bgzip-compressed, tabix-indexed copy of the same GRCh38 release 115 GFF3, with matching options (`--vcf --hgvs --symbol --canonical --no_stats`).
The Ensembl VEP times are those of 29 July 2026, measured on the same Apple M4 with the same image, GFF3, FASTA and options, and were not measured again for this release; only fastVEP's times are those of the release candidate.
The chromosome 22 inputs of fastVEP's series are cut to five columns, which saves it about 3% of its time against the records as they are (50,284 records on one thread: 1.56 s against 1.60 s; `benchmarks/check_lean_inputs.py`); what the July runs of VEP read is not recorded.
Supplementary-annotation conditions supplied ClinVar and gnomAD to fastVEP as native fastSA (`.osa`/`.osa2`) databases and to Ensembl VEP as `--custom` tabix-indexed VCFs.
A single-process whole-genome VEP run exhausts the default Docker memory (7.65 GiB) above approximately 2.7 million variants, so VEP's genome-wide time was obtained by running each chromosome (1-22) separately and summing; every per-chromosome time is the minimum of two independent runs, to remove transient system contention.
The chromosome 22 scaling series (1,000 / 5,000 / 10,000 / 50,284 variants) is the first N variants of the chromosome (`benchmarks/run_head_to_head.py` cuts fastVEP's to five columns).
Because Ensembl VEP requires a tabix index in `--gff` mode -- an unindexed GFF3 is rejected outright -- no unindexed-GFF configuration was benchmarked.

Supplementary-annotation format benchmarks (`benchmarks/run_sa_formats.py`) built the v1 (`.osa`) and v2 (`.osa2`) representations of ClinVar (whole database, release of 27 June 2026) and of REVEL v1.3 (chromosomes 1 and 22, cut out of the source archive) with `fastvep sa-build`, recording on-disk size and build time, and annotated the 673,660 variants of the ClinVar 2-star+ call set against each format, with ClinVar alone and with ClinVar and REVEL, comparing the annotated VCFs by md5 (3 timed runs of each, after one that is not timed and that reads every input; the two formats alternate within a round).

Cross-organism benchmarks used full gene models and FASTA references for yeast (*S. cerevisiae* R64-1-1, Ensembl 115), Drosophila (BDGP6.54, Ensembl 115), Arabidopsis (TAIR10, Ensembl Plants 60), mouse (GRCm39, Ensembl 115), and human (GRCh38, Ensembl 115), and variant call sets from Ensembl/SGD variation (yeast), DGRP2 (Drosophila), the Ensembl Plants variation release 113 (Arabidopsis), the Mouse Genomes Project CAST/EiJ strain (mouse) and GIAB HG002 v4.2.1 (human).
The Drosophila file is in the coordinates of dm3 and the mouse file in those of GRCm38, against gene models of BDGP6.54 and GRCm39: these two benchmarks measure throughput, and the consequences they predict are not those of the variants.

Binary size is that of the release-compiled executable, whose release profile strips symbols.

### 5.3 Accuracy Validation

Accuracy was measured against real Ensembl VEP 116.3 (Docker image `ensemblorg/ensembl-vep:release_116.3`), run in `--gff` mode over a bgzip-compressed, tabix-indexed copy of the GRCh38 Ensembl release 115 GFF3 that fastVEP reads, with the same FASTA, `--tab --force_overwrite --no_stats --symbol --biotype --canonical --numbers --variant_class --show_ref_allele --hgvs --hgvsg`; fastVEP ran with `--output-format tab --symbol --biotype --canonical --numbers --variant-class --show-ref-allele --hgvs --hgvsg`.
`validation/compare_tab.py` pairs the rows of the two files on (`Uploaded_variation`, `Allele`, `Feature`) and compares every shared column but the ones that name the annotation file and the three that a GFF3 cannot fill (`SYMBOL_SOURCE`, `HGNC_ID`, `FLAGS`); it counts the cells that differ for each column and writes every differing row.
The samples are cut from their source call sets by `validation/sample_variants.py`, which takes every k-th record and so is a function of its input (every 200th record of the GIAB HG002 call set, every 5th of the ClinVar 2-star+ call set); the generated worlds are made by the scripts in the `crates/fastvep-cli/fixtures/vep_tab_*` directories (`gen_world.py`, `gen_edges.py`, `gen_lone.py` and others), `validation/run_tab_world.sh` runs both tools over the first of them, and `validation/run_cache_oracle.sh` makes the comparison with VEP's own Ensembl and RefSeq caches for chromosomes 21 and 22.
The comparisons of Section 3.3 were made on 27 October 2026 with the build at commit 5048fc5; `validation/compare_builds.py` runs that build and the release candidate over the inputs and compares their outputs byte for byte, and `manuscript/data/vep116_agreement.csv` and `vep116_hg002_columns.csv` hold the counts, which `manuscript/verify_numbers.py` checks against `docs/VEP_DIVERGENCE.md`.

Every disagreeing row of every comparison is classified in `docs/VEP_DIVERGENCE.md`.
Where the cause is in Ensembl's Perl code, the routine was read, and `_shift_3prime` was extracted from the release 115.1 image and executed on synthetic peptides to confirm the mechanism.

### 5.4 Testing

Tests use Rust's built-in test framework (`#[test]` and `#[tokio::test]`).
The release candidate has 1,733 of them: on macOS arm64 with rustc 1.98.0, 1,731 ran and passed, one was ignored (it needs a file that `fixtures/vep_match/regen.sh` makes) and one is compiled on Linux only (`cargo test --workspace --no-fail-fast --locked`; `benchmarks/results/v0.5.0-rc.1/tests_executed.csv`); the continuous integration runs `cargo fmt`, `cargo clippy -- -D warnings` and `cargo test` on every change.
Tests of compatibility with Ensembl VEP compare fastVEP with VEP's own output, which the repository keeps as golden files made by `regen.sh` scripts that run VEP 116.3 (nine fixtures of generated worlds, 20,363 records, among others), and with patterns of VEP's own test suite (`Parser_VCF.t` and the test VCF files of release 115).
Other tests count the allocations of the per-variant loop with a counting allocator, compare the output of runs on one thread and on many byte for byte, and damage the transcript cache in every way the loader has to refuse.
The standard genetic code implementation was validated by testing all 64 codons against the NCBI translation table 1.
